# 能力扩展设计稿：法规检索（要件呈现）＋ 结构化 ＋ 公文格式

> 开发侧文档 · 不随技能包分发
> 状态：**待用户确认后实施**
> 触发：用户问「都有法规库引擎了，为啥不能法律法规咨询、检索？都有文档引擎了，为啥不能编录撰写某一领域的法规汇编？另外完成剩下两个引擎」

---

## 一、先把「为什么现在不能」说清楚

这不是功能漏做，是三处刻意的边界：

| 诉求 | 现状 | 为什么现在不做 |
|---|---|---|
| 法律咨询／检索 | `legal-verify.py` 只核验不补写 | 库是**审查引法的真值尺**，不是法律数据库。712 条按审查场景精选，不是全集。开放泛化检索，用户问十个问题七个答「库里没有」，信任一次就崩 |
| 法规汇编编录 | `make-docx.py` 按 spec 出件 | 输入是结构化要素，而汇编的输入是「领域」。中间缺一层「领域 → 法条集合」的抽取，**这层正是引擎表 #3 结构化引擎**，它恰恰是规划中的那个 |
| 补齐 #3／#10 | 两者**零实现基础**（已核实：scripts/ 内搜不到任何相关代码；公文仅在 `make-docx.py` 的 `official` 样式里有标题二号居中这类皮毛） | 不是补个函数，是新建两个引擎 |

**结论**：用户的三个诉求指向同一处缺口——缺中间那层结构化能力。所以顺序应为 **#3 结构化 → 法规检索／汇编 → #10 公文格式**。

---

## 二、用户已定的边界（两次确认）

1. **先动咨询检索**，但也补两个引擎。
2. 适用分析口径：**只讲要件，不下结论**——列出条文后逐条说明「本条针对什么情形／适用要件是什么／什么情况下不适用」，**不判断用户具体情形是否构成**。要件是法条客观内容，不是意见。
3. 库外处理：**可联网扩充**——库外来条时联网抓官方源，经双源校验后入临时结果。

---

## 三、对免责声明的冲击（必须先处理）

现行声明逐字为：

> 仅辅助用途，不构成法律意见；须经执业律师复核后方可据此决策。

门禁有 `check_doc_number_caliber` 与**免责声明逐字一致**守卫。一旦引擎产出「适用要件分析」，即便不下结论，也已从「核对引法」跨到「法律信息提供」。**声明不改，守卫就是在保护一句假话。**

拟改（需用户拍板措辞）：

> 本技能提供法律条文检索与适用要件呈现，不构成法律意见、不预测案件结果；具体适用须经执业律师结合事实判断后方可据此决策。

要点：①明确「检索＋要件呈现」而非「意见」；②显式否认结果预测；③保留复核要求。

## 四、新增能力设计

### 4.1 法规检索引擎（#16）— `legal-search.py`

**输入**：自然语言问题 / 法名＋条号 / 关键词
**处理**：
1. 解析意图 → 抽法名、条号、主题词
2. 库内检索：先精确（法名＋条号），再主题词加权（用现有 `_units` 4 字滑窗 + `coverage` 打分，复用 `legal-verify.py` 的算法，不另造）
3. 命中 → 输出原文＋出处＋`verified` 状态
4. 未命中 → **联网扩充链**（见 4.2）

**输出（关键：只讲要件）**：
```
【条文】《民法典》第五百八十五条（现行有效 · 双源已验）
  原文：……
【本条针对的情形】……
【适用要件】（1）……（2）……（3）……
【不适用／除外情形】……
【待律师判断】你的情形是否满足上述要件，本技能不作判断。
```

**红线（写进代码注释与文档）**：
- 要件字段只允许来自条文本身的结构拆解（"……的，应当……" → 要件＋法律后果），**不得由模型自由生成**
- 无「结论」「建议」「胜诉可能」「应当如何」类输出
- 每条必带 `verified` 与出处；未验证的**不得**冒充已验证

### 4.2 库外联网扩充链

```
未命中 → freshness-patrol.py 抓官方源 → legal-parse.py 解析
       → legal-crosscheck.py 双源比对 → 一致才入「临时扩充集」
       → 不一致 → 明示「未验成，需人工核」
```
- 新增安全档位：**L2（不联网就用不成，须显式调用）**——沿用现有四档口径，不改分档定义
- 临时扩充集**不写回** `core/legal-articles.json`（那是随包真值，改动须走开发侧生成链）
- 离线时明示降级：「库内无此条，且当前离线，无法扩充」——不静默假成功

### 4.3 结构化引擎（#3）— `structure.py`

把文档抽成字段树，是**法规汇编的地基**：
- 当事人／金额／期限／违约责任／标的／生效条件
- 输出可校验的 JSON 字段树＋原文定位（每个字段能指回原文哪一句）
- 校验：字段必须有原文锚点，抽不出就留空标「未识别」，**不猜**

### 4.4 法规汇编 → 复用文档撰写引擎

有了 #3，汇编就是：
```
领域 → (结构化的领域要素) → 法条集合（检索引擎给出）→ make-docx.py 按汇编模板出件
```
- 汇编模板：按效力层级分组（法律／行政法规／司法解释／地方性法规），组内按条号
- **只收录库内已验证条文**，库外的标「未收录」并列出，不拿记忆补
- 每条附原文＋出处＋版本日期

### 4.5 公文格式引擎（#10）— `gb9704.py`

GB/T 9704 是公开国标，纯版式规则：
- 版心尺寸、页边距、字体字号（标题二号小标宋、正文三号仿宋）、行距、页码位置
- 出「版式体检表」：逐项对照标准，给出符合／不符合＋偏差值
- 接入 `verify.py` 第四维「格式核验」，把现在的占位变成真判据

## 六、风险与不做的部分

**风险**：
1. **咨询边界最易滑**：一旦允许「要件分析」，下一步就会有人要「我这情况算不算」。代码层面要硬拦：输出结构里根本没有「结论」字段，想写也写不进去。
2. **联网扩充的可靠性**：官方源会改版、会反爬。必须保证「抓不到就明说」，不能降级成模型记忆。
3. **712 条非全集**：任何检索都要显式报「本库覆盖面」，避免用户以为这是法律全库。

**明确不做**：
- 不做「你这种情况应当如何」的结论输出
- 不做全库以外的大规模爬取（只在用户明确问到的条上点查）
- 不在检索结果里混入任何未经双源校验的条文
