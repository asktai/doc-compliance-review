# 下一轮开发计划：make-docx.py 原稿级修订能力（1 修订版 ／ 4 红线修订格式版）

**排期依据**：开发者 2026-10-21 拍板（见 `maint/DEVLOG.md` 第十九轮第六节）。
**现状**：`--source-docx` 仅对 3 清洁版／6 脱敏版／7 照录版生效；1、4 按 SKILL 第三节「原稿底稿硬性要求」走**显式降级**（三处标注「⚠ 降级：非原稿修改」）。

## 目标

1、4 两类在有原稿 `.docx` 时**在原稿上出修改**，不再降级：
- **1 修订版**：在原稿既有 run 之间插入 `w:ins`／`w:del`（Word 原生修订痕迹，修订者＝审查人，可逐条接受/拒绝）。
- **4 红线修订格式版**：以原稿为底，把新增文字标下划线/红字、删除文字标删除线/灰字（不依赖 Word 修订功能）。

## 技术要点（预研结论，待开发时验证）

1. **归因对齐**：审查规格(JSON) 的修改项以**条款定位＋原文片段**锚定；需把每处修改映射到原稿 XML 里的具体 run 边界——同一段落被拆成多个 run（拼写检查、中英混排）时先做 **run 合并预处理**，否则插入位置碎裂。
2. **w:ins/w:del 结构**：`<w:ins w:id w:author w:date>` 包裹新增 run；删除文字放进 `<w:del>` 内的 `<w:delText>`（不是删节点——修订痕迹必须保留删除原文）。id 全文档唯一；author/日期来自审查人＋时间戳。
3. **修订粒度红线**（SKILL 第三节已有）：只标改动的最小范围；整段重写确实无法细分才整段替换，并在批注写明。
4. **批注**：沿用现有口径——标题挂 1 条「这是什么文件」＋每处修改挂 1 条意见批注；3、6、7 仍零批注。
5. **失败回退**：原稿打开失败／run 对齐失败／修改项锚定不到原文 → **自动回退样式档位重建并按降级标注**（沿用现有守卫，不得静默）；回退原因写进文档属性。
6. **守卫与验证**：
   - 单元：构造含多 run 段落、表格内修改、空段落删除、段落首尾修改的样例原稿，逐个断言 XML 结构正确（python-docx 读回 `w:ins`/`w:del` 计数与作者一致）。
   - 端到端：`smoke-test.py` 增 1、4 两类的原稿路线用例（当前只覆盖重建路线）。
   - 负向：坏原稿／锚定失败 → 断言回退＋标注三处齐全。
   - Word/WPS 打开实测：接受全部修订后文本＝清洁版文本（**与 3 清洁版做文本一致性比对**，这是最有力的交叉验证）。

## 验收标准

- `--source-docx` 对 1、4 生效；SKILL 第三节降级情形里"1、4 尚不支持"一条删除；`VERSION.md` / `version.json` 升版（建议 v3.13.0）。
- smoke 全绿；check.py 0 错；接受修订后与清洁版文本一致。
