## 2026-09-24 · V3.8.2 规则计数口径统一 ＋ 生成物污染根治（已发布、已出包）

**起因**：评估技能现状时发现对外宣称的通用库条数与实扫值对不上。深挖后发现不是"漏写 6 条"，而是三脚本的 ID 正则长期漏管整组规则。

**核心缺陷 1：规则 ID 白名单漏组（口径失真）**

| 脚本 | 修复前白名单 | 漏掉 |
|---|---|---|
| `check.py` | `PVLGICDHEQWMNKJSTF` | A(3) B(11) X(5) |
| `rule-baseline.py` | 同上 | 同上 |
| `sample-baseline.py` `CORE_ID_RE` | `…JSTFXB` | A(3) |
| `sample-baseline.py` `RE_RULE` | `…JSTFXB` | A(3) **K(6)** |

即 V3.8.0 才加上去的 K 组，在样例台账识别里从未生效过；A/B/X 三组则从来没被任何一处统计过。

**佐证（不是有意排除）**：`core/01` 第 13 行「规则 ID 约定」早就写明 A 标的与定义、B 通用/杂项、X 逻辑与一致性、K 发票/税务/付款方式——文档承认这些组是真规则，纯属脚本侧漏管。

修复：三脚本各自保留常量但统一为 `CORE_ID_GROUPS = "PVLGICDHEQWMNKJSTFXBA"`（21 组全覆盖）。**真实分布**：A3·B11·C6·D4·E7·F29·G8·H2·I5·J6·K6·L5·M8·N7·P9·Q7·S13·T5·V5·W8·X5 ＝ **159**（文件内 159 行规则、159 个唯一 ID、零重复）。对外口径 **140 → 159**（＝漏的 19 条；规则文本本身一字未改，只纠正计数）。

**核心缺陷 2：白名单无守卫，漂移不可见**

新增一项常驻校验 `check_id_group_whitelist()`：① 三脚本 `CORE_ID_GROUPS` 是否彼此一致；② 是否覆盖 `core/01` 实际用到的全部组字母（双向比对，多退少补都报错）。
另给 `check_rule_metadata()` 补了缺失的一环——原本只校验「生效日/最近修订」两个日期，**不校验规则数**，这正是 140 能长期挂在那里没人发现的原因；现在 `core/01` 元数据写的条数、`README` 对外宣称的条数，都必须等于实扫值，否则 error。

新增后先不修文档，确认它真能抓到错误（**必须先报错、修完文档再转绿**，不能反过来只信写完就绿）：
```
[E] 规则元数据（生效日/最近修订/规则数）缺失或失准：core/01-general-risk-rules.md(缺:规则数写140实为159)
[E] README 宣称通用库 140 条，实际 159 条（两处口径须一致）
```

**核心缺陷 3：生成物污染（与 V3.8.0 修的 `.integrity.json` 同源）**

`core/_rules-baseline.json` 残留在开发侧且被 git 跟踪（total 134 的陈旧版），而 `publish.py` 同步是 **rmtree 后镜像重建**，所以每次发布都把陈旧台账覆盖回运行实例。

诊断中还发现一个此前没意识到的机制：因为先 `rmtree(RUN)` 再 `copytree`，**运行实例原有的生成物会被一并删除**。所以正确的治理不是"排除某个文件名"了事，而是固定流程：

> sync（整目录重建，生成物必然清空）→ **当场重建生成物** → verify → pack

**起因**：用户让做一次 UTF-8 编码体检。查完把发现的三个问题摆出来，用户拍板：
输出**强制 UTF-8**（而非保守的 `errors=replace` 保底），行尾**4 个 py 转 LF**。

### 一、编码体检结论（先说干净的）

| 检查项 | 结果 |
|---|---|
| UTF-8 能否解码 | 56 个文件全过，0 失败 |
| BOM | 0 个 |
| 行尾混用 | 0 个（CRLF 17 / LF 39，各自统一） |
| .py 编码声明 | 18/18 全有 |
| 乱码/替换字符/控制符 | 0 处（`desensitize.py` 的 `××` 是有意占位符） |
| zip 内中文文件名 | 9 个中文条目**全部带 UTF-8 标记**（flag 0x800），Windows 解压不乱码 |
| 外文字符混入 | 52 个文件全书扫描 0 处 |

### 二、查出的真问题

**① 【严重】11/16 脚本无输出编码保护，GBK 下直接崩**

实测复现：`PYTHONIOENCODING=cp936 python3 scripts/smoke-test.py` →
`UnicodeEncodeError: 'gbk' codec can't encode character '\u013c' in position 70`。

崩法是**连环的**，值得记下：子进程（如 `make-docx.py`）无保护 → 按 GBK 吐字节 →
父进程用 `encoding="utf-8", errors="ignore"` 解这些 GBK 字节 → 造出垃圾字符 `\u013c` →
父进程再往 GBK stdout 输出 → 崩。另 `make-docx.py` 里的 `↔`（U+2194）GBK 本就装不下。

作者本人在 Windows 上跑没崩，是因为终端多半走了 UTF-8；**一旦输出重定向到文件
（`> out.txt`）或换台机器就中招**——这类"在我机器上好好的"最该由脚本自己兜住。

处置：12 个脚本（11 个新增 ＋ `version.py` 替换旧块）在 `import sys as _sys` 后统一加：

```python
try:
    _sys.stdout.reconfigure(encoding="utf-8", errors="replace")
    _sys.stderr.reconfigure(encoding="utf-8", errors="replace")
except Exception:
    pass
```

`version.py` 原有旧块只设 stdout、且用 `errors="ignore"`——`ignore` 会静默吞字符，
`replace` 才看得出有字符没出去，故一并替换为统一版。stderr 也设：报错信息同样含中文。

**② 【中】4 个 .py 的 shebang 带 CR**

`desensitize.py` / `make-docx.py` / `make-header.py` / `preprocess.py` 是 CRLF，
shebang 行实为 `#!/usr/bin/env python3\r`。Linux 下直接执行实测：
`/usr/bin/env: 'python3\r': No such file or directory`。
（`python3 scripts/xxx.py` 这种调用法不受影响，故一直没暴露。）
转 LF 后 `./preprocess.py --help` 正常。只动这 4 个 .py，其余 CRLF 的 .md 不动。

**③ 【低】CRLF/LF 不统一**（17 vs 39）—— 无混用，纯风格，未动。

   定下一条原则：**core 无对应条目时不硬套 ID**，宁可直书要点，也不要制造错误的寻址。

### 二、D 盘路径：病灶不在 config.json

用户说"允许自定义但不做强制"。动手前先摸清现状，结果**病灶和预想的不一样**：

- `_config.tool()` 本身早就是"配置路径存在则用、否则回退 PATH"，运行时**从来不强制**；
- 真正的问题在 `_config.py` 的 **`DEFAULTS` 里硬编码着同一套 D 盘路径**。
  V3.8.6 只把随包 `config.json` 清空，却没动 DEFAULTS——config.json 留空时 `load()`
  照样回退到 DEFAULTS，本机路径阴魂不散。难怪那道 check.py 警告一直在。

改法是把"本机"这一层彻底挪出去，三层各司其职：

| 层 | 内容 | 随包 |
|---|---|---|
| `DEFAULTS` | tools 全空 | — |
| `config.json` | tools 全空 | ✔ |
| `config.local.json` | 本机自定义 | ✘ 不进 git、不随包 |

- `_config.load()` 三层叠加，任一層坏了跳过它用上一层（不阻断主流程）
- `detect-tools.py --write` 改写本机覆盖层；新增 `--write-config` 留给"整包拷走"
- `check.py` 由"路径不存在即告警"改**三级**：有效→info；失效但 PATH 可兜→info；PATH 也没有→才 warn
- `check_hardcoded_paths()` **取消对 `_config.py` 的豁免**——DEFAULTS 既已清空，
  任何 .py 都不该再出现盘符字面量，从此谁再塞本机路径进代码会被当场抓住
  （`check.py` 自身仍豁免，检测正则自指无法自检）

### 三、验证

- 四种情形分级全对：自定义有效／路径失效但 PATH 可兜／tools 留空／无覆盖层
- `check.py` **警告 1 → 0**（那道 D 盘路径警告消失）
- 冒烟 **89/0/0**，且这次**没有手动清空 config.json**——默认值本身就是干净的
- 出包后离线解包：包内 `config.json` tools 全空、无 `config.local.json`、
  **脚本内盘符字面量 0**（含 `_config.py`）
- 解包环境端到端：`detect-tools.py --write` → 生成覆盖层且 `config.json` 保持全空 → `check.py` 0 警告
- 规则库新内容随包核实：住改商 2 处、自力救济 4 处、引用瑕疵残留 0、meta V1.5.0

**附带收益**：升级不必再备份本机工具路径（新版包压根不含 `config.local.json`）；
整包拷给别人也是干净的默认值。文档（README／教程 3.2／升级章节／排错表）同步改写。

## 2026-09-24 V3.10.1 技能介绍卡重排（修文字堆叠）＋ 剩余遗留收口

### 一、用户反馈：卡片"文字堆叠，文字哪看的清楚啊"

不凭感觉改，先**量**：写了个排版审计器（临时工具，不进包）拦截 Pillow 的 text 调用，
把主画布上每段文字还原成包围盒两两比对。1080×1440 上 73 个文字块，实测三个病灶：

1. **主标题与副标真实重叠 8px**——主标题 60px 字身框 y 96~183，副标 34px y 175~225。
   根因：**CJK 字身框高约为字号的 1.45 倍**（60px→87px），旧代码按"字号"估算标题占到哪一行
   （注释里写"排到约 168"），估算偏小。这类错肉眼查不出几何，一量就有数。
2. **字号普遍偏小**——最小 15px、正文 17.5px。卡片按 480px 宽预览时等效 **6.7px**、
   360px 宽等效 5.0px，缩略即糊。这才是"哪看的清楚"的主因。
3. **密度过高**——12 条列表＋12 个 chips＋页脚 4 行挤一版。

### 二、改法：先量后画，字号换密度

- **K 组从独立圆角卡改为 chips 区内金色高亮一组**：信息一条不丢（发票与税率·三流一致／
  银行承兑·红字冲红／虚开发票红线 ★★★），省掉一整块卡壳的 123px，全数还给字号与行距。
- 字号整体上调：正文 17.5→**22**、chips 17→19、页脚 16→18；定位语 19→22。最小字号 15→17。
- **墨迹盒定位**：所有文字改按"基线＋em 盒"推算位置（基线上 0.88em、下 0.12em），
  不再按字身框拍脑袋；副标/定位语的纵坐标由上一行的**墨迹底**推导，不写魔法数。
- **先量后画**：先把各段高度算出，再把剩余空间平均分给段间空隙（含收口）——
