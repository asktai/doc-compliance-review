| **v3.25.6** | 2026-10-26 | **产出物「只有一个格式」的定位与修复：不是 bug，是静默默认值——改为必须问**。用户在千问办公反馈「技能产出物为何变成只有一个格式的了」。实测复现：不传 `--formats` 出 3 个文件全是 .docx，传全则出 15 个（3 类 × 5 种），**代码本身 5 种格式全部可用**。查下来**不是缺陷**：`make-docx.py` 的 `--formats` 默认值为 `docx`，而 SKILL 第 486 行上方明写「不选或回「默认」→ 仅 WORD」——**文档与代码字面一致**，且该默认值自 v3.7.1 起就是如此，门禁此前从不报错。真正的问题在路径：格式在开场清单第 9 项（Qn+8）收集，「清单收口后不再追问，仅当跳过清单时才在产出前确认一次」——用户直接上传文档说「审查」时清单被跳过，落到默认值，且**全程没有任何提示告诉他本可以要更多**。经用户选择，采纳「不改默认值，改为强制询问」：SKILL 文件格式节新增**产出前必收**规则（与「审查人名称」同级）——清单已收则按清单执行，**清单被跳过或该项未答时产出前必须问一次**，用户回「默认」即按 WORD 出，但这一问不能省；**纯自动化**（无人可问）时免问，但须在产出后如实说明本次只出了 WORD 并列出其余 4 种。新增守卫 `_check_format_default()`，判据刻意**不守措辞而守事实**：① 代码 `--formats` 的 default 值必须能在 SKILL 找到登记；② 缺省时「必须问」。**守卫自身补了反向漏洞**：首版只判「默认窄、文档没写」，注入「把 default 改成 5 种、文档仍写仅 WORD」时门禁全绿——漏报；补为双向判。另记一条：修文档时新写的说明句含「实际 1 格式」字面，被既有守卫 `(\d+)\s*种?\s*格式` 抓为「写 1 种」与「5 格式」打架——**守卫没错，是我的文案不当**，文档里不该同时出现两种格式口径，已改为「到手只有 Word」。README「一句话流程」同步补「清单被跳过时格式须产出前问一次」。门禁 0 错 0 警、冒烟 183/0/7 全绿。 |
| **v3.25.5** | 2026-10-26 | **修 Windows 装机冒烟 8 项全灭的编码缺陷（千问办公实测报告）**。v3.25.4 包在千问办公装机后：文件与指纹全对、check.py 0 错 0 警，**装机冒烟却是 175 通过／8 失败**——8 项全报「门禁无输出（退出码 0）」。诊断成立：`check.py` 两处门禁自检子进程（巡检自检／条号对位）用 `subprocess.run(..., text=True)` 却未指定 encoding，**Windows 下 text=True 默认按 locale（GBK）解码**，而本技能所有脚本输出 UTF-8——中文报告一进管道就乱码，JSON 解析失败 →「门禁无输出」。**开发侧（Linux 全 UTF-8）一个错都不报**，问题只在用户机器上炸，这正是「在我机器上是好的」的教科书形态。修三件事：① 六处 subprocess 调用统一补 `encoding="utf-8"`（`errors="replace"` 优于 `ignore`——ignore 静默吞字节，replace 至少留痕），`run_gate` 的子进程 env 再加 `PYTHONIOENCODING=utf-8` 两端锁死；② **假绿洞**：`run_gate` 在门禁无输出时返回 `errs=[]`，正向用例（断言 errs 为空）会把「门禁没跑成」误判为「通过」——改为 errs 带上说明，负向正向两端都失败；③ 新增守卫 `_check_subprocess_encoding()`：`text=True` 必须伴随**恰好一个** encoding——判据按括号配平抓完整参数区（按行 grep 会被多行调用骗）。**这道守卫立起来的过程中自己炸了一次**：修复时 make-docx 的 soffice 调用续行里原本就有 encoding，按行 grep 误判为缺、又塞一个，`keyword argument repeated` 直接把冒烟炸成 33 项失败——**冒烟当场抓住**，故判据定为「恰好一次」既拦缺失也拦重复。冒烟恢复 183/0/7，门禁 0 错 0 警。 |
